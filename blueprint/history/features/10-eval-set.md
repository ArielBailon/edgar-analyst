# Feature: Eval set

**From build-plan:** feature 10
**Build attempt:** 1
**Status:** verified
**Branch:** `feature/eval-set`

## Goal

Produce the hand-labeled ground truth item 11's eval runner will later score
against: 20-50 question/expected-answer/expected-citation triples, grounded in
the filings and transcripts already ingested for AAPL, MSFT, and TSLA. This
feature only produces that data and its structural model; it does not run the
retrieval/generation pipeline against it or score anything (that's item 11).

## In scope

- `app/eval/` (new package): `__init__.py`, `models.py` defining `EvalPair`
  (`question: str`, `expected_answer: str`, `expected_citation: Citation`,
  importing `Citation` from `app.retrieval.models`), and `test_models.py`
  proving it round-trips, matching `app/generation/test_models.py`'s pattern.
- `app/eval/eval_set.json`: a JSON array of 20-50 hand-authored `EvalPair`
  records. Each `expected_answer` and `expected_citation` must be grounded in
  real content already indexed under `data/chunks/{AAPL,MSFT,TSLA}/*.json`
  (real section text, real `chunk_id`, real date), spanning multiple companies
  and both filings and transcripts, not invented facts.
- `app/eval/test_eval_set.py`: a structural test proving the file has between
  20 and 50 records, every record parses as a valid `EvalPair`, and no two
  records repeat the same `question`. See Notes for the AI for why this test
  does not also check the records against the live corpus.

## Out of scope

- The eval runner (item 11): running each pair through retrieval, generation,
  and the refusal path, and scoring citation correctness and answer relevance.
  This feature produces only the ground truth it will consume.
- Any refusal-path / unanswerable case in the eval set. `EvalPair.expected_citation`
  is a required `Citation` per the data model in `project-overview.md`, so
  every record here is an answerable question with a real citation; there is
  no `should_refuse` flag or similar in the established contract, and adding
  one is a new API contract this feature doesn't own.
- Storing the file under `data/`. `.gitignore` has a blanket `data/` rule for
  regeneratable ingestion artifacts (chunks, filings, transcripts); this
  hand-authored ground truth has to be committed and can't be regenerated by a
  pipeline, so it lives under `app/eval/` instead. See Notes for the AI.
- CSV storage. The data model allows CSV or JSON; JSON is the existing
  convention for structured pipeline output in this repo (`data/chunks/*.json`,
  loaded the same way in `app/embedding/pipeline.py`), and avoids inventing a
  flattening scheme for the nested `Citation`.
- Cross-checking every `expected_citation.chunk_id` against the real local
  index or `data/chunks/` as part of the automated pytest suite. See Notes for
  the AI for why.
- Query logging (item 12) and the README (item 13).

## Data / contracts

Existing contract this feature consumes, unchanged:

- `app.retrieval.models.Citation`: `company`, `document_type` (`"10-K"` |
  `"10-Q"` | `"transcript"`), `section`, `date`, `chunk_id`.

New contract introduced here:

- `app.eval.models.EvalPair`: `question: str`, `expected_answer: str`,
  `expected_citation: Citation`. Matches `project-overview.md`'s `EvalPair`
  data model exactly; no additional fields.
- `app/eval/eval_set.json`: a JSON array of `EvalPair`-shaped objects (plain
  dicts with `question`, `expected_answer`, and a nested `expected_citation`
  object), 20-50 entries. This is the file item 11's eval runner will load.

## Testing

`AGENTS.md` declares `Test: pytest`. Both steps add testable structure and

## Notes for the AI

- Why not `data/`: `.gitignore` ends with a blanket `data/` rule for
  regeneratable ingestion output. `app/eval/eval_set.json` is hand-authored
  ground truth with no regenerating pipeline, so it must be committed; putting
  it under `data/` would silently exclude it from every commit, including this
  feature's own.
- Why `test_eval_set.py` doesn't check the corpus: `AGENTS.md`'s fresh-clone
  setup explicitly promises "`pytest` passes with no further setup. The suite
  needs no network, no ingested data, and no embedding model." `data/chunks/`
  is gitignored and won't exist on a fresh clone or in CI, so a test that reads
  it to verify each `chunk_id` is real would break that guarantee for everyone
  who hasn't run the ingest and chunking pipelines locally. Ground each pair in
  the real corpus by hand while authoring it (the corpus is available locally
  right now, at `data/chunks/`), but don't make that grounding a pytest
  assertion.
- Pull real text for `expected_answer` from the chunk's `text` field rather
  than paraphrasing from memory; the whole point of this ground truth is that
  it's actually true against the ingested source, the same standard the
  refusal path (feature 7) and answer generation (feature 6) hold the system
  itself to.
- Type hints on every signature, pydantic for the new model, `snake_case`
  functions, `SCREAMING_SNAKE_CASE` constants if any are needed, no em dashes
  anywhere in code, comments, or docs.
